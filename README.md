# Defense.Planning — 저장소를 가로지르는 과제의 관리 체계

이 폴더는 `Defense.Unity` · `Defense.Design` · `Defense.Logs` 저장소와 작업 공간에 걸치는 **과제(P-nn)** 의 검토 · 결정 · 계획 · 진행 상태 · 세션 인계를 담는다 — 마일스톤 단위의 작업 계획이다. 게임 기획(기획서 · 데이터 표 · 목업)은 [`../Defense.Design/`](../Defense.Design/README.md)(X-02). 2026-10-29 신설. 체계는 EasyCheck.Planning(`~/UBM/z.docs/EasyCheck.Planning`, 2026-09-22~)을 그대로 가져왔고, 이 게임에 맞게 바꾼 것만 7절 X-nn 에 적는다. 세 게임 공통 결정(G-nn)은 `../../../_공통/README.md`. 작업 공간의 에이전트 지침은 루트 [`CLAUDE.md`](../../CLAUDE.md)(정본 [`_템플릿/루트_CLAUDE.md`](_템플릿/루트_CLAUDE.md)).

각 저장소 안의 규약 — `CLAUDE.md` · `z.docs/dev/milestone/` · `z.docs/work_reports/` · 커밋 규칙 — 은 **그대로 둔다.** 이 폴더는 그 위의 층이다. 저장소 하나로 끝나는 일은 여기 만들지 않는다.

## 4. 지칭 · 표기 규칙

- **과제**는 `P00` 처럼 두 자리. **마일스톤은 저장소 접두를 반드시 붙인다**: `DEF-M01`(Unity 저장소). 다른 게임의 같은 번호와 섞이지 않게 접두는 게임마다 다르다(Defense `DEF` · AirShooter `AIR` · RideShooter `RIDE`).
- **커밋 제목 과제 태그**: 저장소 규약 `verb: 제목` 을 지키면서 `verb: [P01] 제목`. 트레일러는 저장소 `CLAUDE.md` 대로(결정 전은 `_공통` Q-01).
- **경로**: 문서끼리는 그 문서 위치 기준 상대경로. 저장소 파일은 작업 공간 루트 기준 `Defense.Unity/Assets/Scripts/Core/WaveDirector.cs:42` 처럼 경로 + 줄 번호.
- **근거 표기**: 직접 파일을 열어 확인한 것은 ✔, 조사 에이전트 보고를 옮긴 것은 △(착수 전 확인), 추정은 [추정]. 검토서에는 표기를 생략하되 기술근거에는 반드시 붙인다.
- **날짜 접미** `_YYYYMMDD` 는 시점 문서(검토서 · 계획서 · 기술근거 · 지시서)에만. 살아 있는 문서(README · NOTES · 결정기록 · 보류작업 · 작업색인)에는 붙이지 않는다.
- **지시서 파일 이름**: `02_계획/지시서/YYYYMMDD_Sn_제목.md` — 작성일 접두 · Sn = 계획서 분할표의 세션 번호(`S1` · `S3a`) · 제목 = 저장소 · 마일스톤 · 일. 계획 밖 임시 지시서는 `YYYYMMDD_제목.md`.
- 비밀값(키 · 서명 자료) 금지. 이모지 금지. 한글은 그대로 쓴다 — 유니코드 이스케이프로 넣지 않는다.
- 작업 보고서 프론트매터의 `work_unit` 에는 과제 ID(`P01`)를 쓴다.

## 5. 한 에이전트로 두 저장소를 다루는 규율

### 5.1 세션 시작
1. 이 README 의 현황판. 2. [`NOTES.md`](NOTES.md) 「다음 세션 시작 전 확인」 · 「사용자 대기」. 3. 작업할 과제의 `NOTES.md` 같은 절. 4. 손댈 저장소의 `CLAUDE.md` 와 마일스톤 문서. (루트 `CLAUDE.md` 가 같은 순서를 지시한다.)

### 5.2 작업 중
- **저장소 안 규칙은 그 저장소 `CLAUDE.md` 가 우선한다** — 계획 제시 후 승인 · 작업 보고서 · 커밋 · 코드 컨벤션 · 테스트 규율. 이 폴더는 그것을 대체하지 않는다.
- **커밋은 저장소별로 따로** 한다. 제목에 과제 태그 `verb: [P01] 제목`. 한 세션에서 저장소 둘 이상을 고쳤으면 세션 끝에 `03_작업기록/작업색인.md` 에 저장소별 커밋을 **한 표**로 남긴다.
- **저장소 간 협의 문서(handoff)는 쓰지 않는다.** 한 에이전트가 양쪽을 고치므로 요청 · 회신이 없다.
- **Unity 에디터 · 빌드는 주 세션(오케스트레이터)만 만진다.** 서브에이전트는 코드 · 컴파일 · 테스트까지(루트 `CLAUDE.md` 「공유 자원」).
- **코드 리뷰는 세 층이고 센서는 세션이 스스로 띄운다.** 커밋 전 결정론 게이트 · 자기 점검, 코드를 커밋한 세션은 보고 전에 세션 센서(읽기 전용 리뷰어 1 · 고위험이면 리뷰어 2 + 검증 1), 통합 · 머지 세션은 `main` 머지 전에 세션 사이 어긋남 · 고위험 경로만 — [`코드리뷰_가이드.md`](코드리뷰_가이드.md). 자원 보호가 자동화보다 우선(에이전트 5 초과면 묻는다).
- 검색은 `Defense.Unity/Library` · `Temp` · `Logs` · `obj` · `Builds` 와 `../Defense.Logs/sessions` 를 제외한다.

### 5.3 병렬 실행
- **분할 단위는 저장소**가 기본이다. 같은 Unity 프로젝트를 나눌 때는 계획서의 분할표에 파일 영역을 명시한다(겹침 0). **씬 · 프리팹 파일은 한 에이전트만** 만진다(YAML 충돌은 사람이 못 푼다).
- 코어의 공개 API 가 확정되기 전에는 병렬로 돌리지 않는다.
- worktree 격리는 저장소 `CLAUDE.md` 규칙 그대로. `Library/` 는 worktree 마다 새로 생기므로 첫 열기가 느리다.
- 서브에이전트에 넘기는 프롬프트는 [`_템플릿/작업지시서.md`](_템플릿/작업지시서.md) 골격으로 쓰고 `02_계획/지시서/` 에 파일로 남긴다.
- **서브에이전트 보고는 산출물로 검산한다** — 파일을 열고, 컴파일하고, 플레이 화면을 본다. 특히 "있다 / 없다 / 완료" 주장.

### 5.4 세션 종료
1. 과제 `NOTES.md` 덮어쓰기 3절 갱신. 2. 새 결정은 `결정기록.md` 에 D-nn, 보류는 `보류작업.md` 에 H-nn. 3. `03_작업기록/작업색인.md` 에 저장소별 작업 보고 경로 · 커밋 추가. 4. 이 README 현황판의 상태 · 다음 행동 · 갱신일. 5. 손댄 저장소마다 `git status` 가 깨끗한지 확인. 6. 수행이 끝난 지시서를 `02_계획/지시서/_old/` 로 옮긴다(`git mv`) — 과제 README 표의 링크도. 보류된 지시서는 제자리에 두고 「보류」 표시.
