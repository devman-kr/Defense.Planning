# C# 코딩 표준 Unity 화 검토서

**과제** P00 · **작성** 2026-10-30 · **상태** 검토 완료 — 결정 대기

**이 문서의 위치**: EasyCheck.Server 에서 가져온 C# 코딩 표준 사본([`../../_템플릿/Unity_csharp_coding_standards.md`](../../_템플릿/Unity_csharp_coding_standards.md), 커밋 `caf8ac8`)을 Unity 6 모바일 게임 · 공개 포트폴리오 · 코어 복사(G-07) 전제에 맞게 고치기 위한 검토다. 절마다 유지 · 수정 · 교체를 정하고, 사용자가 정할 것만 6절에 모았다. 결정이 끝나면 P00 [결정기록.md](../결정기록.md) D-nn 으로 적고 표준을 고친다. 근거는 이 문서 끝 「근거」.

**읽는 사람**: 결정자(1 · 5 · 6절) · 표준을 고칠 세션(4 · 7절).

**용어**: 표준 = EasyCheck 판 사본(절 번호 I~XXII 는 그 문서 기준) · 템플릿 = `_템플릿/Unity_CLAUDE.md`(장차 `Defense.Unity/CLAUDE.md`) · 가이드 = `코드리뷰_가이드.md`(영역 코드 `SAVE` · `LIFE` … 는 그 부록 A) · 계약 = P01 계획서 2절의 기획 데이터 표 ↔ ScriptableObject 계약(K1~K6).

## 1. 결론

표준 22절(과 기본 원칙 · 경계 네이밍 소절) 가운데 그대로 두는 것 2, 고치는 것 13, 서버 전용이라 Unity 규칙으로 바꾸는 것 9 이고, 표준에 없던 Unity 전용 절 7개를 새로 쓴다. 사용자 습관(POCU 계열 — `var` · `??` · `using` 선언 · `new()` 금지, `OrNull`, `Debug.Assert`, `async void` 금지)은 Unity 와 부딪히지 않으므로 유지하고, Unity 가 강제하는 네 가지는 반드시 바꾼다 — ① 직렬화는 프로퍼티가 아니라 필드(XX절이 거꾸로다) ② `UnityEngine.Object` 에는 `?.` 도 금지(XV절은 허용) ③ 코루틴의 `IEnumerator` 는 `System.Collections` 예외(V절이 금지) ④ 모든 public 메서드의 진입 · 종료 로그(X절)는 게임 루프에서 성립하지 않는다. 공개 포트폴리오 저장소라서 파일 헤더 변경 이력 · `@devman 날짜` 인라인 표식 · `[Developer]` 어트리뷰트는 뺀다 — 이력은 git 과 작업 보고서가 맡는다(템플릿 「주석」과 같은 결정). 결과물은 가이드 영역 코드 10개를 전부 덮는 절 구성으로 다시 짜서, 센서 지적이 「표준 몇 절」을 인용할 수 있게 한다.

### 4.4 형식과 자리

- **형식**: 지금 사본처럼 규칙만 적는 요약형을 유지한다(9.8 KB → 12 KB 안팎 목표). Unity 전용 규칙에는 한 줄 「왜」를 붙인다 — 공개 저장소에서 심사자가 읽고, 다음 세션이 규칙을 완화할 때 근거가 된다(결정 13).
- **정본 자리**: 권장 — 지금 자리(`_템플릿/Unity_csharp_coding_standards.md`)가 정본, `Defense.Unity/z.docs/dev/csharp_coding_standards.md` 가 사본(템플릿 `Unity_CLAUDE.md` 와 같은 방식, X-01). 다른 두 게임은 P00 을 복사할 때 가져간다(D-02). 제언 — `_공통/_템플릿/` 로 올려 세 게임 공통 정본(G-08)으로 두고 게임 이름 자리는 `<게임>` 으로 쓴다. 지금은 게임이 하나라 이득이 없고, Core 복사(G-07) 때 표준도 같이 복사되므로 권장안이 단순하다(결정 1).
- **템플릿과의 분담**: 템플릿 「코딩」 7줄은 「꼭 필요한 것」(폴더 · asmdef · 금지 셋)만 남기고 표준을 가리킨다. 같은 규칙을 두 곳에 적지 않는다.
- **자동화**: 표준은 규칙이지 게이트가 아니다. `.editorconfig`(들여쓰기 · Allman · `var` 선호 · using 정렬)는 계획서 S2 D1 7번 「우리 파일」에 더한다. 금지 패턴 소스 스캔 EditMode 테스트는 가이드 9절 후속 작업 그대로.

### 4.5 추기 2026-10-30 — 표준을 쓰고 센서(S1b)를 거친 뒤 4절과 달라진 것

- **4.1 IX · XVI `PlayerPrefs`**: 「설정값만 허용」에서 **「쓰지 않는다」**로 — 기획서 6.1 이 설정도 저장 파일 하나에 두므로 한 파일이 백업 · 복구 · 버전 관리에 단순하다(표준 §12.6, D-06 ⑤ 비고).
- **4.2 비동기 · 코루틴**: 「소유 컴포넌트가 비활성화되면 멈추므로 `OnDisable` 에서 정지」는 전제가 틀렸다 — 코루틴은 GameObject 비활성화 · 파괴로 멈추고 `enabled = false` 로는 안 멈춘다(Unity 매뉴얼, 표준 근거 5). 표준 §9.3 · §14.3 이 맞는 문장이다.
- **4.1 XIII · D-06 ⑥ `InternalsVisibleTo`**: 「테스트 asmdef 에」를 **어셈블리마다 자기 테스트 어셈블리**로 구체화 — Core 는 `Devman.Core.Tests.EditMode`(코어와 같이 복사), Game 은 `Defense.Tests.EditMode` · `PlayMode`. Core 의 IVT 에 게임 이름이 들어가면 §1.1 「코어에 게임 이름 없음」과 부딪힌다(센서 #7).
- **4.4 분량**: 「12 KB 안팎」은 지키지 못했다 — 32 KB(원문 9.8 KB). 신설 7절 · 번호 인용용 항목 번호 · 「왜」 19줄 · 근거 11행이 더해졌고, 한글 UTF-8 은 글자당 3바이트다. 요약형(규칙 한 줄)은 유지했다. 더 줄일지는 사용자 읽기(승인 지점 2)에서.
- **4.1 에 없던 규칙(작성 세션이 더함 — D-07 비고, 사용자 확인 대기)**: `??=` 금지 · `ReferenceEquals` 금지 · `Resources/` · `StreamingAssets/` 폴더 금지 · `DateTime.Now` 로직 금지 · 코루틴 `Routine` 접미 · 문자열 `StartCoroutine` 금지 · 「코어 소속이 애매하면 Game」. POCU 의 「`Async` 접미 금지」는 넣지 않았다.
- **4.1 XII 싱글톤 · 4.1 XX 직렬화**: 풀은 직접 만들지 않고 엔진 내장 `UnityEngine.Pool.ObjectPool<T>`(§9.1). 직렬화 금지 목록에 가변 배열 · 중첩 컨테이너 추가(§12.1, 매뉴얼).
- **4.1 IX `default:`**: Core 는 `NotImplementedException` 이라는 구분을 버리고 전부 `Debug.Assert` + `LogError` + 안전값, 빠진 열거값은 EditMode 전수 테스트(§6.8 · §15.3) — MonoBehaviour 에서 Core 를 부르는 경로에서 예외가 나는 것을 막는다(센서 #17).
- **영역 코드**: 절 머리 대괄호는 리뷰 영역에 속하는 절에만 — 이름 · 서식 · 주석 절은 없음(센서 #22 · #23).

## 8. 위험과 전제

- **C# 9.0 전제**(Unity 6000.3). Unity 가 CoreCLR 로 올라가 언어 버전이 바뀌어도 금지 목록은 「습관」이라 유지되고, 미지원 항목(레코드 · `init`)만 다시 본다.
- **표준은 게이트가 아니다.** 지키는지는 세션 센서와 사람이 본다. 반복 지적은 EditMode 소스 스캔 테스트로 내린다(가이드 9절 후속).
- **직렬화 규칙을 어기면 조용히 깨진다** — 프로퍼티는 저장되지 않고, SO 런타임 변경은 에디터에서 에셋을 바꾼다. 둘 다 컴파일 오류가 없으므로 표준 + 테스트로만 막는다.
- **UI 프레임워크(UI Toolkit 대 uGUI)가 미정**이라 UI 절은 비워 두고 `DEF-M01` 전에 채운다.
- 표준과 템플릿에 같은 규칙이 두 번 적히면 한쪽이 낡는다 — 4.4 분담을 지킨다.
