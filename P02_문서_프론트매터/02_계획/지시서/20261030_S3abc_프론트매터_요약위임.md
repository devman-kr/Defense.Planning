## 프롬프트 본문 (여기부터 붙여 넣는다)

이 지시서는 Sonnet 5.5 기준으로 썼다(가이드 확인일 2026-10-30). 세션 모델이 다르면 보고 첫 줄에 알린다.

### 맡는 일

세 게임 작업 공간의 모든 마크다운 문서 맨 앞에 YAML 프론트매터를 붙이는 중이다. 규약은 `/Users/devman/_Projects/_Personal/Games/_공통/문서규약.md`(이하 규약). 경로 · git 이력으로 채울 수 있는 칸은 이미 채웠고, **사람의 판단이 필요한 칸 — `id` 의 slug · `summary` · `status` — 을 네가 문서를 읽고 채운다.** 이 요약은 다음 세션들이 파일을 열지 않고 문서를 고르는 데 쓰인다. 결과는 리드가 검사하고 사용자가 표본을 본 뒤 문서에 붙인다 — 문서 파일은 네가 고치지 않는다.

### 입력과 산출

- 입력 = 산출: 제안 JSON 한 파일(맡는 범위 칸의 경로). 최상위는 목록이고, 항목 하나가 문서 하나다 — `{"path": Games 루트 기준 경로, "fields": {...}, "block_from": null, "note": ""}`. Games 루트는 `/Users/devman/_Projects/_Personal/Games`.
- **목록의 모든 항목**에 대해 아래 「채우는 법」을 한다. 항목 순서 · 수 · `path` · `block_from` · 이미 채워진 `created` · `updated` · `work_unit` 은 바꾸지 않는다.
- 끝나면 같은 파일에 같은 구조로 다시 쓰고, `python3 -I -c "import json,sys; json.load(open(sys.argv[1]))" <파일>` 로 읽히는지 확인한다.

### 채우는 법

1. **문서를 읽는다.** `Read` 로 연다. 300줄이 넘는 문서는 앞 150줄과 절 제목(`grep -n '^#'`)으로 판단해도 된다.
2. **`id`** = `<created 의 숫자 8자리>-<slug>`. slug 는 영소문자 · 숫자 · 하이픈 2~40자(정규식 `^[a-z0-9-]{2,40}$`)이고 문서를 알아볼 수 있는 영어 낱말로 짓는다. 접두를 붙인다 — 과제 폴더 문서 `p00-…` · `p01-…`, Design `design-…`, Unity 저장소 `unity-…`, `_공통` `common-…`, Planning 루트 문서 `planning-…`, AirShooter `air-…`, RideShooter `ride-…`, 작업 공간 루트(git 밖) `ws-…`. 파일 하나에 id 하나, 이 JSON 안에서 겹치지 않게.
3. **`summary`** = 한 문장, **200자 이하**(공백 포함 글자 수 — `len()`). 제목을 되풀이하지 말고 내용을 적는다 — 시점 문서(검토서 · 계획서 · 지시서 · 코드리뷰 기록)는 「무엇을 검토 · 결정 · 지시 · 지적했는지」, 살아 있는 문서(README · NOTES · 결정기록 · 가이드 · 장부)는 「무엇을 담는지」. **본문에만 나오는 고유명사를 하나 이상** 넣는다 — 파일 이름 · 결정 번호(D-nn · G-nn · X-nn) · 식별자 · 도구 이름. 첫 문단을 그대로 베끼지 않는다. 한글로 쓰고 한글을 유니코드 이스케이프로 쓰지 않는다. `{` `}` 는 쓰지 않는다.
4. **`status`** = 규약 7절. 시점 문서 — 결정이 끝난 검토서 · 승인된 계획서 · `_old/` 로 옮겨진 지시서 · 코드리뷰 기록은 `final`, 결정 대기 검토서 · 승인 전 계획서 · 아직 실행 전인 지시서(`지시서/` 바로 아래)는 `draft`. 살아 있는 문서는 `final`. 본문이 다른 문서로 「대체」 되었다고 밝히면 `deprecated`. 판단 근거가 문서에 없으면 `final` 로 두고 `note` 에 「status 근거 없음」.
5. **`title`** 은 이미 H1 에서 뽑았다. H1 이 없어 파일 이름에서 만들었거나 120자를 넘으면 문서 내용으로 고친다.
6. **`doc_type` · `lifecycle`** 은 경로로 정했다. 규약 3절 표로 보아 틀렸으면(예: 경로 관례에 안 맞아 빈 문자열) 고치고 `note` 에 한 줄 이유를 적는다.

### 검증 (보고 전에 스스로)

다음을 한 번에 확인하는 짧은 파이썬을 돌리고 결과를 보고에 붙인다 — 항목 수가 처음과 같다 · 모든 `id` 가 `^\d{8}-[a-z0-9-]{2,40}$` 이고 앞 8자리가 `created` 와 같다 · id 가 겹치지 않는다 · 모든 `summary` 가 1~200자 · `status` 가 `draft` · `final` · `deprecated` 중 하나 · `title` 이 1~120자.

### 금지

- 문서 파일(`.md`) · 규약 · 다른 에이전트의 JSON 을 고치는 것. 고칠 것이 보이면 `note` 에 적는다.
- git 명령으로 상태를 바꾸는 것, 새 파일을 만드는 것(맡은 JSON 하나만 다시 쓴다), 네트워크.
- 요청하지 않은 일(문서 내용 고치기 · 링크 채우기 · 태그 달기 — 이행 때 링크 · 태그는 채우지 않기로 했다). 끝나면 멈추고 보고한다.

요청한 것이 끝날 때까지 계속한다. 멈추는 것은 JSON 을 읽을 수 없거나 문서가 없을 때뿐이다.

### 보고 형식

한글로, 결론부터.

1. 한 줄 결론(완료 / 부분 / 막힘)과 채운 항목 수
2. 검증 결과(위 파이썬 출력)
3. `doc_type` · `lifecycle` · `title` 을 바꾼 항목과 이유
4. 확신이 낮은 요약 · status 목록(경로와 까닭)
5. `note` 에 남긴 것 가운데 리드가 알아야 할 것
