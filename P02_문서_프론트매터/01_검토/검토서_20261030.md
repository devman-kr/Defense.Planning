# 문서 프론트매터 규약 검토서 — Clew 문서 규약 접목

**이 문서의 위치**: 사용자가 2026-10-30 「모든 마크다운 문서에 프론트매터가 있어야 한다」고 정하고, 예전에 만든 Clew 저장소에서 접목할 것을 찾으라고 했다. 이 문서는 그 분석과 방안이다. 실행 순서 · 세션 분할 · 승인 지점은 [계획서](../02_계획/계획서_20261030.md)에 있고, 승인되면 세 게임 공통 결정(`_공통` G-nn — 문서 규약)과 [결정기록](../결정기록.md)으로 옮긴다. 파일 단위 근거는 이 문서 끝 「근거」.

**읽는 사람**: 결정자(1 · 4 · 6절) · 규약을 만들 세션(4 · 7 · 8절).

**용어**: Clew = 사용자가 2026-09 EasyCheck 문서를 위해 만든 문서 검색 엔진 · MCP 서버(Python, M01~M08 중 M07 까지 완료). 규약 = 이 과제가 만들 `_공통/문서규약.md`. 시점 문서 · 살아 있는 문서 = Planning README 4절의 구분(파일 이름 날짜 접미 유무). 과제 상태 = 과제 README 의 검토 · 계획 · 실행 …(문서 상태 `status` 와 다르다).

이 문서는 규약을 처음 따르는 문서다 — 위 프론트매터가 규약의 첫 사례이고, 템플릿의 머리줄(**과제** · **작성** · **상태**)은 프론트매터와 겹쳐 쓰지 않았다(4.4).

## 1. 결론

- Clew 에서 가져올 것은 검색 엔진이 아니라 **기획서 5장 「문서 규약」**이다. Clew 는 스스로 「검색 품질의 상한은 알고리즘이 아니라 작업 단위와 링크를 프론트매터에 적는 규율이 정한다」고 결론 냈고, 우리 문서는 134건(Clew 코퍼스 4,154건의 3%)이라 `rg` 로 찾을 수 있다.
- 필드 이름은 Clew 와 같게 두고(나중에 Clew 를 붙일 길을 남긴다), 어휘와 작업 단위만 우리 체계 — 과제 ID `P02`, 시점 · 살아 있는 문서 — 에 맞춘다.
- 강제는 글이 아니라 설정으로 한다. 문서를 쓰는 주체가 대부분 에이전트이므로, 쓰는 순간 검사하는 훅(PostToolUse)과 커밋 전 린트로 지킨다. 훅은 기존 문서를 모두 옮긴 뒤 켠다.
- 순서는 규약 · 템플릿 → 도구(린터 · 이행 스크립트 · 로그 훅) → 기존 134건 이행 → 훅 · 엄격 모드(계획서 S1~S4). 같은 날 P00 이 종결 절차(작성자 재작성 · GitHub 첫 푸시)에 들어가 이 일은 새 과제 P02 로 두었고, 사용자가 P02 를 P00 의 남은 일보다 먼저 이 세션에서 서브에이전트와 함께 하기로 정했다.

## 4. 방안

### 4.1 Clew 에서 배운 것

| 배운 것 | Clew 근거 | 이 프로젝트에서 |
|---|---|---|
| 프론트매터가 메타데이터의 정본이고, 경로 · 파일명 추론은 보조다 | 기획서 §4.7 | 도구 없이 `rg '^summary:'` 하나로 문서 목록이 된다 |
| 문서 id 와 경로를 분리하고 링크는 id 로 건다 | §4.2 | 지시서를 `_old/` 로, 과제를 `z.completed/` 로 옮길 때마다 링크를 손으로 고치는 일이 준다 |
| `summary` 가 가장 값진 한 줄 — 본문의 고유명사를 넣는다 | §5.2 | 맥락 없이 시작하는 세션이 파일을 열지 않고 고른다 |
| `status`(draft · final · deprecated)와 `lifecycle`(static · living)을 나눈다 | §5.4 | 우리의 「시점 문서 · 살아 있는 문서」와 1:1 로 맞는다 |
| 역방향 링크는 사람이 쓰지 않는다 — 양쪽을 손으로 쓰면 반드시 어긋난다 | §4.3 | 링크는 한쪽에서만 건다. 거꾸로 보기는 도구 몫 |
| 린트 통과가 값이 온전하다는 증거는 아니다 — 따옴표 없는 `#` 이 summary 를 잘랐는데 통과했다 | M07 진행 메모 「배운 것」 | 위험한 맨 값(` #` · `: `)을 따로 잡는다 |
| 되풀이되는 실수는 기록 · 메모리 · 다짐이 아니라 설정(훅)으로 막는다 | M07 · `block_python_stdin.py` | 쓰는 순간 검사하는 훅. Clew 의 최대 리스크(사람이 YAML 을 안 씀, §12.1)가 우리에겐 작다 |
| 같은 규칙을 두 벌 두면 반드시 갈린다 | M03 진행 메모 | 프론트매터와 겹치는 본문 머리줄을 템플릿에서 지우고, 린터 어휘와 규약 표는 시험 하나로 묶는다 |
| 도구가 형식을 정한 파일은 따로 다룬다 | M07 — `SKILL.md` 가 필수 필드 오류로 남음 | Claude 메모리 · `.claude/agents` · 스킬은 예외 |

### 4.2 필드 — Clew 이름을 그대로, 값만 우리 체계로

```yaml

id: 20261030-p02-review-frontmatter
title: 문서 프론트매터 규약 검토서 — Clew 문서 규약 접목
summary: 한 문장, 200자 이하, 본문의 고유명사 하나 이상
doc_type: review
status: draft
lifecycle: static
created: 2026-10-30
updated: 2026-10-30
work_unit: P02
---
```

| 필드 | 필수 | 규칙 | Clew 와 다른 점 |
|---|---|---|---|
| `id` | 필수 | `YYYYMMDD-slug`(날짜 = `created`, slug = 영소문자 · 숫자 · 하이픈 2~40자). 바꾸지 않는다. 한 게임 작업 공간과 `_공통` 안에서 유일 — 같은 id 는 바이트까지 같은 사본일 때만 | 사본 규칙을 더함 |

| `doc_type` · `status` · `lifecycle` | 필수 | 4.3 어휘 · draft · final · deprecated · static · living | 어휘만 다름 |
| `created` · `updated` | 필수 | ISO 날짜. updated 는 본문을 고친 날 | 같음 |
| `work_unit` | 조건부 | 과제 ID(`P02`). 과제 폴더 안 문서는 그 폴더 ID 와 같아야 하고, 작업 보고서는 필수(과제 밖 작업은 `AD-HOC`). 등록부는 Planning 의 과제 폴더 목록 | `EC-26-041` 형식 · `work_units.yaml` 대신 |

| `milestone` | 선택 | `DEF-M01` | 같음 |
| `work_type` · `commits` | 작업 보고서만 | 기존과 같음 | 같음 |
| `tags` | 선택 | X-03 영역 코드 10개(`SAVE` · `ECON` · `LIFE` · `TIME` · `PERF` · `INPUT` · `CONTRACT` · `TEST` · `UI` · `BUILD`)만 | 태그 사전 대신 이미 정한 어휘 재사용 |

### 4.4 템플릿 · 정본 · 사본

- **템플릿**(`_템플릿/` 에서 복사해 새 문서를 만드는 것 — 검토서 · 결정기록 · 계획서 · 과제 NOTES · 과제 README · 작업지시서)의 프론트매터는 만들어질 문서의 골격이고 값 자리는 `{…}` 다. `_템플릿/` 밖에서 `{…}` 가 남으면 오류다. 템플릿 본문의 머리줄 가운데 프론트매터와 겹치는 것(**작성** · **상태** · **과제**)은 지운다. 과제 README 의 **상태**는 과제 단계라 둔다.
- **정본 · 사본**(상위 · 작업 공간 · Unity 저장소 `CLAUDE.md`, 코딩 표준)은 프론트매터까지 같은 파일이다. 정본을 고치고 복사하는 지금 방식(G-08 · X-01)은 그대로 두고, 같은 id 가 두 곳에 있으면 린터가 바이트를 대조해 어긋남을 잡는다.
- `Unity_README.md` 는 공개 첫 화면의 골격이라 예외 파일을 만든다 — 자기 프론트매터를 갖되 복사할 때 블록을 뗀다고 본문에 적는다.

### 4.5 검사와 강제

- **린터** `_공통/_도구/fm_lint.py` — 표준 라이브러리만, 평평한 `키: 값` · `[목록]` 만 읽는다. 종료 코드 0 · 1(경고) · 2(오류)는 Clew 와 같다.
- **규칙** — Clew L01~L08 · L10~L13 · L15 를 가져오고(작성자 · 팀 · 레지스트리 규칙 L09 · L14 · L16 은 뺀다), 다섯을 더한다: ① 같은 id 사본의 바이트 대조 ② `_템플릿/` 밖의 자리표시 `{…}` ③ 따옴표 없는 ` #` · `: ` ④ 한글 유니코드 이스케이프(CLAUDE.md 「한글은 그대로」를 설정으로) ⑤ 본문 상대 링크 대상 없음(경고 — 로그 · 템플릿 제외). 그 밖에 우리 규칙 둘 — 과제 폴더 안 문서의 `work_unit` = 폴더 ID, 파일 이름에 날짜 접미가 있으면 `static`(Planning README 4절).
- **강제 지점** — ① PostToolUse 훅이 세션이 `Write` · `Edit` 한 `.md` 를 바로 검사해 문제를 세션에 돌려준다 ② 커밋 전 린트 오류 0(스크립트 · `cp` 로 만든 파일은 훅이 못 보므로) ③ 이행이 끝나면 프론트매터 없음(L01)을 경고에서 오류로.
- **어휘는 두 곳** — 린터 상수와 규약 표. 둘이 같은지 보는 시험을 하나 둔다(Clew 는 어휘를 코드에 고정하고 기획서에 따로 적었다).

### 4.7 기존 문서 이행

- Clew `migrate` 를 따른다 — 경로 관례 · git 이력(첫 커밋일 = `created`, `--follow` 로 이동 전까지, 마지막 커밋일 = `updated`)으로 초안을 만들고, `summary` 는 문서를 읽고 쓴다. 첫 문단을 자동으로 잘라 만든 요약은 Clew 에서 잡음이었다(§6.4).
- **본문은 손대지 않고 앞에 블록만 붙인다**(Clew `--apply`). 쓰기 전후 본문 바이트를 대조한다. 살아 있는 문서의 머리줄 중복(기획서의 「판」 줄 등)은 다음에 고칠 때 정리하고, 그래서 `version` 은 이행 때 채우지 않는다.
- 저장소마다 `docs:` 커밋을 따로 한다. 로그 저장소는 다른 세션이 없을 때.
- 기존 Unity 보고서 3건은 프론트매터만 고친다(링크 id · 태그 영역 코드 · summary 200자).
