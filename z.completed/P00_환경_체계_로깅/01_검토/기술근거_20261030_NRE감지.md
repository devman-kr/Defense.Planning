# NullReferenceException 조기 감지 — 기술근거

**과제** P00 · **작성** 2026-10-30 세션 8(Opus 5.5) · **결정** [`../../README.md`](../../../README.md) 7절 X-04 · **구현** P01 `DEF-M01`

**이 문서의 위치**: 사용자 질문 두 개(2026-10-30)에 대한 웹 조사와 저장소 규칙 대조다 — 「NRE 를 개발 단계에서 일찍 감지하는 기법」, 「모든 작업을 세션이 unity-cli 로 하는 환경에서 감지하는 방법」. 표기: ✔ 직접 확인(로컬 파일 · 명령) · △ 웹 검색 요약 또는 웹 조회 에이전트 보고(구현 전에 원문 · 실측으로 확인) · [추정].

---

## 1. 결론

세션은 인스펙터 · 콘솔 창을 보지 못한다. 그래서 감지를 전부 「명령 → 텍스트 결과」로 두고, 네 시점에서 막는다.

| 시점 | 장치 | 잡는 것 | 세션이 읽는 곳 |
|---|---|---|---|
| 코드 수정 → 컴파일 | Microsoft.Unity.Analyzers DLL(`RoslynAnalyzer` 라벨) + `Assets/Default.ruleset` 으로 UNT0007 · 0008 · 0023 · 0029 를 Warning 고정 | Unity 객체에 `??` · `?.` · `??=` · `is null`(표준 §6.3 위반) | 게이트 「새 경고 0」 — `Logs/gate-editmode.log` grep · `console status` |
| 씬 · 프리팹 연결 직후 | 직접 만든 `[Required]` + `validate_references` `[CliCommand]` | 필수 필드 None · Missing(연결 대상 삭제) · Missing Script | 명령의 JSON 결과 |
| 커밋 전 게이트 | 같은 검증의 EditMode 테스트 · PlayMode 스모크 | 실행 중 NRE · `Awake` 단언 실패(§7.9) | `test run` 결과 · `unity test` 종료 코드 |
| 빌드 | `IPreprocessBuildWithReport` 에서 빌드 씬 전체 검증 → `BuildFailedException` | 빌드에 들어가는 씬의 연결 누락 | `unity build` · `build status` 결과 |

못 잡는 것: 스모크가 지나가지 않은 코드 경로(커버리지 패키지로 볼 수 있다 — 승인 지점), 예외 없이 틀리게 도는 것(스크린샷 · 플레이검사 몫).

## 2. 기법별 근거

| # | 기법 | 내용 | 표기 |
|---|---|---|---|
| 1 | Unity 의 `==` 재정의(가짜 null) | 파괴된 객체를 null 로 본다. `?.` · `??` 는 이 재정의를 거치지 않는다 | △ Unity 블로그(2014) — 표준 §6.3 근거 2 · 3 과 같은 내용 ✔ |
| 2 | Microsoft.Unity.Analyzers 규칙 | UNT0007 Null coalescing · UNT0008 Null propagation · UNT0023 Coalescing assignment · UNT0029 Pattern matching with null(모두 Correctness). UNT0039 「자기 `GetComponent` 면 `RequireComponent`」. 표준 §6.3 의 `ReferenceEquals` 금지에 맞는 규칙은 없다 | △ 규칙 목록 원문(웹 조회 에이전트) |
| 3 | 분석기를 Unity 컴파일에 넣기 | NuGet 직접 설치는 안 된다 — DLL 을 `Assets` 에 넣고 `RoslynAnalyzer` 라벨. 범위는 asmdef 로 제한 | △ Unity 6 매뉴얼 |
| 4 | 심각도 | `Assets/Default.ruleset`(전체) · `<어셈블리>.ruleset`(asmdef 옆). `Action` = Error · Warning · Info · None. 바꾼 뒤 스크립트 재임포트. 6000.x 의 `.editorconfig` `dotnet_diagnostic.<ID>.severity` 는 [추정 — 검색 요약만] | △ Unity 매뉴얼 2020.3 ~ 6000.x |
| 5 | Error 로 올리지 않는 이유 | 컴파일 오류가 남은 채 에디터가 켜지면 Safe Mode — Pipeline 이 로드되지 않아 `unity command` 가 끊긴다 | ✔ unity-cli 스킬 `integration-advanced.md` 「Recovering from Safe Mode」 |
| 6 | 직렬화 참조 검증 | 공식 내장 도구는 찾지 못했다. 커뮤니티: NaughtyAttributes `[Required]`(MIT) · unity-notnullattribute(유지 중단) · Better Validation. 판정: ObjectReference 속성이 `objectReferenceValue == null` 이고 `objectReferenceInstanceIDValue != 0` 이면 Missing, 0 이면 None. 컴포넌트 목록의 null 은 Missing Script | △ 판정식은 커뮤니티 PR 한 곳 — 일부러 깨뜨린 프리팹으로 확인 |
| 7 | `OnValidate` · `[RequireComponent]` 의 한계 | `OnValidate` 는 열지 않은 씬에서 다시 저장할 때까지 불리지 않는다. `[RequireComponent]` 는 붙이는 순간만 확인한다 | △ |
| 8 | Test Framework 의 로그 실패 | 테스트 중 일반 Log · Warning 이 아닌 로그(Error · Assert · Exception)가 나오면 기본으로 실패(`LogAssert`). 의도한 로그는 `LogAssert.Expect` | △ Test Framework 1.6 · 2.0 문서 |
| 9 | 열린 에디터에서 테스트 | `TestRunnerApi.Execute` + `ICallbacks.RunFinished`. Pipeline 의 `test run` 이 이 경로 | `test run` ✔ S2 실측 · API △ |
| 10 | 빌드 중단 | `IPreprocessBuildWithReport` 에서 `BuildFailedException`. 일반 `Exception` 으로는 빌드가 멈추지 않는다는 포럼 · 이슈 기록 | △ |
| 11 | 빌드에서만 나는 NRE | 씬이 빌드 목록(빌드 프로필)에 없음 · `Editor` 폴더 에셋 참조 | △ 커뮤니티 블로그 |
| 12 | 단언 | `Debug.Assert` · `Assert.IsNotNull` 은 `UNITY_ASSERTIONS` 조건부 — 개발 빌드에 기본 포함 | △ — 표준 §6.9 근거 4 ✔ |
| 13 | 도메인 리로드를 끈 경우 | static 이 플레이 사이에 남는다 → `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` 로 초기화. Project Auditor 「Domain Reload」 화면이 문제 코드를 찾는다(6.4 내장 · 이전은 패키지) | △ |

## 3. 이 저장소 규칙과의 관계 ✔

- **Nullable 참조 형식은 쓰지 않는다.** 표준 §5.5 가 `#nullable` 을 금지한다(UnityEngine API 에 null 주석이 없고 가짜 null 을 표현하지 못한다). 세션 답변(2026-10-30)에서 「순수 로직 asmdef 에만 `csc.rsp` `-nullable:enable`」로 제안했던 것을 이 대조에서 뺐다.
- 표준 §6.3(Unity 객체는 `== null` · `!= null` 만)은 지금 사람 · 센서가 보는 규칙이다. 2번 분석기가 그중 `??` · `?.` · `??=` · `is null` 을 컴파일 경고로 바꾼다 — `Defense.Unity/CLAUDE.md` 「검토 기준」의 「반복 지적은 테스트 · 분석기로 내린다」.
- 표준 §7.9(`[RequireComponent]` · 필수 참조는 `Awake` 에서 `Debug.Assert`)와 §6.7(메시지 경로에서 던지지 않는다)은 그대로다. `Debug.Assert` 는 LogType.Assert 라 8번에 따라 PlayMode 스모크를 실패시킨다 [추정 — 첫 스모크에서 확인].
- 게이트 명령은 `Defense.Unity/CLAUDE.md` 「결정론 게이트」 한 곳(X-03 ①). X-04 는 장치만 정하고, 명령은 `DEF-M01` 구현 때 그 절에 넣는다.
- 분석기 DLL 은 외부 파일이라 `ASSETS.md` 장부에 올린다(G-02). 나머지 장치는 직접 작성한다.

## 4. S2 실측과의 대조

세션 답변에서 「S2 에서 확인할 것」으로 셋을 제안했으나 S2 는 같은 날 다른 세션에서 이미 끝나 있었다.

| # | 확인할 것 | 결과 |
|---|---|---|
| 1 | 에디터가 열려 있으면 `unity test`(batchmode)가 거부되나 | ✔ 거부 — 종료 6 `already open in a running Editor`(`Defense.Unity/CLAUDE.md` 「결정론 게이트」) |
| 2 | Pipeline 에 코드 실행 · 콘솔 · 테스트 명령이 있나 | ✔ `script eval --code` · `console status`(오류 · 경고 수) · `test run --mode editor\|playmode` · `editor.playmode start\|stop`(명령 166개). **남음**: 콘솔 개별 메시지(예외 본문 · 스택)를 읽는 명령이 있는지 — `DEF-M01` 첫 PlayMode 스모크 때 `--detail full --format json` 목록에서. 없으면 `Logs/` 의 에디터 로그를 grep 한다 |
| 3 | `csharp-ls` 가 Unity 생성 csproj 의 분석기 진단을 보여 주나 | **남음** — `csharp-ls --diagnose` 의 `.slnx` 로드는 ✔(S2 작업 보고 7절), 정의 이동 · 호버도 미확인(P00 NOTES 4번). 분석기를 넣은 뒤 같이 본다 |
