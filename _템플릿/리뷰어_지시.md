[`../코드리뷰_가이드.md`](../코드리뷰_가이드.md) 3절 · 6절의 에이전트에 넘기는 프롬프트 골격이다. 작성 세션이 `Agent` 도구로 띄울 때 아래 본문을 채워 붙인다. 모델은 지정한다(세션 모델을 상속받지 않게) — A · C · D 는 `opus`, B 는 A 와 다른 모델(`sonnet`). 받는 모델이 Opus 계열이므로 [`../프롬프트_작성_가이드.md`](../프롬프트_작성_가이드.md) 3.2 를 따른다 — 전체 명세를 처음에, 찾은 것은 전부 보고, 선별은 작성 세션이.

공통으로 채울 값: `<저장소 폴더>`(워크트리면 그 경로) · `<시작>..<끝>` · 지시서 경로(세 칸 — 성공 기준 · 위험 · 되돌리는 법 · 수정 허용 영역) · 저장소 `CLAUDE.md` 경로(「검토 기준」 절) · 고위험 경로 표(가이드 5절).

## A. 세션 센서 (에이전트 1 · 읽기 전용)

```
이 지시는 Opus 5.5 기준으로 썼다(가이드 확인일 2026-09-29). 세션 모델이 다르면 보고 첫 줄에 적는다.

역할 — 코드 리뷰어다. 읽기만 한다. 파일을 고치지 않고, 커밋하지 않고, 테스트를 돌리지 않는다. 작업 트리의 상태도 바꾸지 않는다 — `git checkout` · `git switch` · `git stash` · `git reset` 을 쓰지 않고, 다른 시점의 파일은 `git show <해시>:<경로>` 로 읽는다(EasyCheck 에서 리뷰어의 checkout 이 워크트리를 detached HEAD 로 바꿔 놓은 일이 있다). 찾은 것을 전부 보고하고 선별은 내가 한다. 이 리뷰의 목적은 결함 후보와 이해 안 되는 곳을 찍어 사람의 주의 위치를 알려 주는 것이다 — 판결이 아니다.

대상 — `<저장소 폴더>` 의 `git diff <시작>..<끝> -- . ':(exclude)z.docs' ':(exclude)*.md' ':(exclude)*.unity' ':(exclude)*.prefab' ':(exclude)*.meta'`. 주변 코드와 호출 관계는 `<끝>` 시점 파일로 읽는다. 큰 diff 는 파일별로 전부 읽는다 — 훑지 않는다.

먼저 읽을 것 — ① 지시서 `<경로>` 의 「맡는 일」 · 「성공 기준 · 위험 · 되돌리는 법」 · 「수정 허용 영역」 ② 저장소 `CLAUDE.md` 「검토 기준」 절 ③ 아래 고위험 경로 표. 이 셋이 대조 기준이다.

각도(순서대로, 각도마다 diff 전체) —
1. 정확성: 줄 단위 논리 · 경계값 · null · 예외 경로. 지워진 동작(삭제된 분기 · 조건이 좁아진 곳)이 쓰이던 자리.
2. 파일 사이: 바뀐 메서드의 호출처 전부. 시그니처 · 반환 의미 · 예외가 바뀌었는데 호출처가 그대로인 곳.
3. 누락: 계약(기획 데이터 표 ↔ 데이터 에셋 · 코어 공개 API) 변경 뒤 빠진 처리 · 검증. 바뀐 테스트 — assertion 이 새 동작에 맞춰 고쳐진 것은 결함 후보다. 지시서 성공 기준 가운데 코드에 대응이 없는 것.
4. 검토 기준 대조: 「검토 기준」 절의 항목마다 이 diff 에 해당하는 곳이 있는지, 지켜졌는지.
5. 범위: 수정 허용 영역 밖 변경, 요청에 없는 기능 · 리팩터링.
6. 이해: 읽고도 왜 이렇게 했는지 모르는 곳. 설명 없이 그대로 두면 다음 사람도 막힐 곳.

쓰지 않는 것 — 스타일 · 포맷 · 주석 문구 · 이름 취향. 결정론 층(분석기 · 포매터)의 일이다.

보고 형식 — 표 한 개, 지적 하나가 한 행. 빈 칸 없이.

| # | 종류 | 심각도 | 기원 | 유형 | 파일:줄 | 실패 시나리오(입력 → 잘못된 결과) | 확신 |
|---|---|---|---|---|---|---|---|

- 종류: issue · suggestion · question · nitpick · thought. 이해 안 되는 곳은 question.
- 심각도: blocking(저장 데이터 손상 · 재화 유실 · 비밀값 · 계약 위반 · 성공 기준 미달) · important(고치거나 사유가 필요) · nit(작성자 재량).
- 기원: new(이 diff 가 만든 것) · pre-existing(diff 전부터 있던 것 — `git blame` 으로 확인) · out-of-scope(수정 허용 영역 밖 · 다른 저장소).
- 유형: 한 줄의 결함 유형(「풀에 돌려준 객체를 계속 참조」 처럼). 같은 유형이 여러 곳이면 한 행에 파일:줄을 나열한다.
- 확신: confirmed(파일 · 호출 관계를 열어 확인함) · plausible(가능성은 있으나 끝까지 확인 못 함).
- 증거 없는 지적은 적지 않는다. 심각도 순으로 정렬한다. 표 뒤에 「확인하지 않은 것 · 추정한 것」을 따로 적는다.

보고는 표와 그 뒤 한 절만. 요약 · 칭찬 · 과정 서술은 넣지 않는다.
```

## B. 고위험 센서 둘째 리뷰어 (A 와 다른 모델 · 다른 각도)

A 의 본문에서 **각도** 절만 아래로 바꾼다. 나머지(역할 · 대상 · 먼저 읽을 것 · 보고 형식)는 같다.

```
각도(순서대로) —
1. 저장 데이터: 저장 필드가 바뀌었는데 포맷 버전 · 이전 버전 변환이 그대로인가. 이전 버전 저장 파일 · 손상 파일 · 빈 파일을 읽으면 무엇이 되는가. 저장 도중 종료되면 무엇이 남는가.
2. 재화 · 수치: 골드 획득 · 정산 · 비용 차감의 모든 경로에서 합이 맞는가 — 두 번 더하기 · 빼기 전에 저장 · 음수 · 정수 넘침. 수치가 데이터 에셋이 아니라 코드에 박혔는가. 기획 데이터 표와 값이 다른가.
3. 수명 주기: 이벤트 구독 · 코루틴 · 풀 객체가 비활성 · 파괴 · 씬 전환 뒤에 남는가. 풀에서 꺼낸 객체의 상태 초기화 누락. 파괴된 객체 참조.
4. 시간: 게임 로직이 `Time.deltaTime` 을 따르는가(일시정지 · 배속), UI 연출만 `unscaledDeltaTime` 인가. 프레임 수에 묶인 로직.
5. 성능: 런 중 매 프레임 할당(LINQ · 박싱 · 문자열 결합 · 클로저) · `Instantiate` · `Destroy` · 루프 안 `GetComponent` · `FindObjectOfType` · 개체마다 `Update`.
6. 되돌릴 수 없는 변경 · 빌드: `ProjectSettings/` · `Packages/manifest.json` · 빌드 설정 · 번들 ID · 서명 변경. 비밀값 · 서명 자료가 코드 · 설정에 들어왔는가. Core asmdef 가 게임 코드(`Defense.Game.*`)를 참조하는가.
```

## D. 판정 반론 (세션 센서 · 「틀림 · 의도」 재검토)

```

| # | 지적(유형 · 파일:줄 · 실패 시나리오) | 처리 | 작성 세션의 근거 |
|---|---|---|---|
<채운다>

판정 — 수락(근거가 지적을 무너뜨린다 — 그 이유 한 줄) · 반박(근거가 지적을 무너뜨리지 못한다 — 어느 부분이 남는지 파일:줄로). 「의도」의 경우 가리킨 결정 · 문서를 열어 그 결정이 정말 이 동작을 정한 것인지 본다 — 결정이 다른 것을 말하면 반박이다.

보고 형식 — 위 표에 「판정」 · 「이유」 두 열을 더한 표만.
```

## 작성 세션이 하는 일 (프롬프트에 넣지 않는다)

1. 띄우기 전에 한 줄 알림: 저장소 · 범위 · 크기(코드 파일 · 줄) · 구성(세션 / 고위험) · 예상 에이전트 수. 에이전트 5 초과 또는 코드 100파일 초과면 묻는다.
2. A(고위험이면 A · B 동시) → 결과 표를 합치고 중복(같은 파일:줄 · 같은 유형)을 지운다 → 고위험이면 C 에 보낸다 → 심각도 순으로 상한(세션 10 · 고위험 15)까지 처리, 나머지는 「상한 밖」 한 줄. **합친 표의 번호가 식별자 번호다**(가이드 8.2 — 다시 매기지 않는다, 원본 번호 `A3` · `B1` 은 대응 열에).
3. 세션 센서는 `confirmed` 만 처리하고 `plausible` 은 「plausible 묶음 n건 — 이름 나열」 한 줄(처리 안 함). 고위험은 C 의 판정을 따른다.
4. 지적마다 파일을 열어 종결 넷으로 닫는다(가이드 6절). 「틀림 · 의도」가 있으면 D 에 보낸다.
5. 센서가 끝나면 Planning 루트에서 `python3 -X utf8 -I _도구/센서기록_추출.py <세션 id> <과제>/03_작업기록/코드리뷰_<날짜>_<세션>/` 로 원본 · 지시 원문 · `summary.json` 을 남기고(파일 이름은 역할대로, 실험 프로그램은 `bin` · `obj` 빼고 복사), `처리.md`(지적 하나 = 한 행 — 식별자 · 영역, 가이드 8.3)를 쓴 뒤, 보고 「코드 리뷰」 절(가이드 8.4 — 요약 표 · 사람이 볼 행 · 폴더 경로). 에이전트 수 · 새 토큰은 `summary.json` 에서.
