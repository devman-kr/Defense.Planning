# Pnn 과제 계획서 — 제목

**작성** YYYY-MM-DD · **근거** [검토서](../01_검토/검토서_YYYYMMDD.md) · [기술근거](../01_검토/기술근거_YYYYMMDD.md) · [결정기록](../결정기록.md) D-nn까지 반영
**규모 표기**: S = 반나절 이하 · M = 1~2일 · L = 3일 이상

**이 문서의 위치**: 검토서의 방안을 세 저장소의 마일스톤과 작업으로 쪼갠다. 저장소 안 상세 설계는 각 저장소 마일스톤 문서(`z.docs/dev/milestone/NN. slug/`)가 정본이고, 이 문서는 그것들을 **한 과제로 묶는 층**이다 — 어느 저장소가 무엇을 어떤 순서로, 계약은 무엇이 바뀌고, 병렬로 돌릴 수 있는 것은 무엇이며, 끝났다는 것을 어떻게 확인하는가.

## 2. 계약 변경 (API.Spec)

한 에이전트 체계에서 저장소 간 협의 문서를 대신하는 절이다. **계약이 확정되기 전에는 클라이언트 작업을 병렬로 돌리지 않는다.**

| # | 변경 | 종류 | API.Spec 파일 | 서버 구현 | 소비자 | 상태 |
|---|---|---|---|---|---|---|
| C1 | `POST /api/…` 신설 | 신설 / 필드 추가 / 의미 변경 / 폐기 | `api/<도메인>/POST_….md` · `model/….md` | DEF-Mnn.k | Console · App | 초안 / 확정 / 커밋(해시) |

- 공통 규약(snake_case JSON · `*_at` UTC · 페이징 · 에러 형식)은 `../../../EasyCheck.API.Spec/README.md`.
- API.Spec 커밋은 **서버 작업 세션이 할 수 있다**(루트 `~/_Projects/_Personal/Games/Defense/CLAUDE.md` 「저장소를 가로지를 때」). 그 밖의 경우는 사용자가 한다. push 는 늘 사용자. 세션이 커밋하지 않았으면 서버 작업 보고에 "명세 미커밋" 절을 남긴다.

## 3. 순서와 의존

```
S1 ─┐
    ├─ S2 ─ S3(서버 계약 C3 확정 후 콘솔 · 앱 병렬)
S4 (법무 결론 후)
```

| 순서 | 작업 | 저장소 | 의존 | 규모 | 위험 등급 | 병렬 가능 |
|---|---|---|---|---|---|---|
| 1 | | | | | 저 · 중 · 고 | |

- **분리 규칙**: Dockerfile · `.gitlab-ci.yml` 같은 인프라 변경과 파괴형 마이그레이션은 기능 변경과 **따로 머지 · 배포**한다(P01 머지 뒤 배포 4일 지연의 원인). 세션 하나는 리뷰 가능한 크기(코드 50파일 · 5,000줄 안)로 자른다 — 넘으면 세션을 나누거나 지시서에 센서 영역 표를 둔다(`../코드리뷰_가이드.md` 2절).

## 4. 분할표 (병렬 실행용)

세션(에이전트) 하나 = 한 행 — 행 번호 `1` · `2` · `3a` 가 지시서 파일 이름의 `Sn` 이 된다. **저장소 단위 분할이 기본.** 같은 저장소를 나누면 파일 영역이 겹치지 않아야 한다. 지시서는 `지시서/YYYYMMDD_Sn_제목.md` 로 남긴다(`../_템플릿/작업지시서.md`, X-16).

| 세션 | 저장소 · 브랜치(worktree) | 파일 영역(수정 허용) | 읽기 전용 | 산출물 | 검증 방법 | 금지 |
|---|---|---|---|---|---|---|
| A | Server · `p01/s2-tier` | `Services/…`, `Controllers/…`, `Migrations/` 신규 | API.Spec, 정책 문서 | 커밋 + 작업 보고 | `dotnet test --filter "Category!=Integration"` 통과 | 공유 DB 시딩 · 서버 기동 |

오케스트레이터(주 세션)만: 공유 DB · 서버 프로세스 · 테스트 계정 · 시딩 · 머지.
